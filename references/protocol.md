# Igloo Notify Protocol Specification

## Topic Resolution Hierarchy

When an agent or script dispatches notifications or starts a listener, the topic is resolved strictly in the following priority order:

1. **CLI Explicit Argument**: `--topic <name>`
2. **Environment Overrides**: `NTFY_TOPIC`, `NTFY-TOPIC`, `NTFY_REMOTE_TOPIC`, `NTFY-REMOTE-TOPIC`
3. **Project Context**: Target project root `.env` under `<PROJECT>-NOTIFY` (or `IGLOO_V2_NOTIFY`)
4. **User Secrets**: `~/.env.secrets` under `NTFY[-_]REMOTE[-_]TOPIC`
5. **Session Default**: `vonalato`

## Topic Confidentiality & Guardrails

- **Topic Pattern**: Must strictly match `^[A-Za-z0-9_-]{1,64}$` or standard UUIDv4.
- **Secret Isolation**: Topics must be treated as credentials. They must never be checked into git, echoed in unredacted error dumps, or stored in public tracking issues.
- **Git Hygiene**: Project `.env` files storing topic keys must always be listed in `.gitignore`.

## Severity and Priority Mapping

| Severity Level | ntfy Priority | Default Tag | Intended Usage |
|---|---|---|---|
| `progress` | 2 (Low) | `hourglass_flowing_sand` | Non-blocking background steps, intermediate task progress |
| `normal` / `P3` | 3 (Default) | `information_source` | Milestones, task completion, standard terminal reports |
| `warning` / `P2` / `P1` | 4 (High) | `warning` | Recoverable errors, retried operations, missing configuration |
| `urgent` / `P0` | 5 (Max) | `rotating_light` | Critical failure, security denial, execution halt |

## Reflection Loop Suppression

To prevent infinite message echoing between the agent and the ntfy pub/sub stream:
1. Every message generated by `notify_bridge.py` automatically carries the tag `robot` and a recognized title prefix (`[Aggs]` or `[Agent]`).
2. When `remote_bridge.py` listens to incoming stream events, any event containing tag `robot` or bot title patterns is immediately skipped and logged to `seen_<topic>.txt`.
3. Unique message IDs are persisted to disk to prevent duplicate ingestion across listener reconnects.

## Interactive Ingestion Gate & Remote Input Elevation Protocol

### 1. Mandatory Strict Yes/No Gate
Before spawning a background listener or ingesting inbound responses, the agent MUST ask the user:
> *"Should I accept answers / listen for remote replies from you on topic `<topic>` as direct instructions to me? (yes/no)"*

### 2. User Approval ('Yes')
- Spawns `scripts/remote_bridge.py --topic <topic>` as a daemon task.
- Establishes full semantic input equivalence: all incoming events tagged `🚨 [REMOTE NTFY USER INPUT] 🚨` are treated directly as user instructions to the agent.
- The agent must react to inbound user commands by executing requested tools, querying information, or steering ongoing operations without requiring separate confirmation.

### 3. User Rejection ('No')
- The agent operates in outbound notification mode only via `scripts/notify_bridge.py`.
- No listener daemon is started. Any external events posted to the topic are ignored and not piped into the conversation context.
